# Social login for IllamHelp members

**Release decision, 26 November 2026.** Keep IllamHelp password accounts on every platform. Use the existing Keycloak realm for member identity and sessions. Staff use a separate client and authentication policy.

| Release surface | Sign-in options to ship |
| --- | --- |
| Desktop and mobile web, including Safari | Username or email + password, Google, and Facebook once its public configuration passes testing. Apple web sign-in is deferred. |
| Google Play Android app | The same options as web. The reviewed Play policies cover account access, privacy and deletion. We found no equivalent-provider mandate for ordinary social login. [Play review access](https://support.google.com/googleplay/android-developer/answer/15748846) · [User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311) |
| App Store iPhone app | Username or email + password, plus Google and Facebook alongside native Sign in with Apple. Apple is our chosen equivalent privacy-preserving login under guideline 4.8. If it is unfinished, submit a first-party-only iOS build and restrict the corresponding hosted client to first-party login and registration. [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/#login-services) |

Apple evaluates data collection, private email at signup and consent for advertising-related tracking. Changing the sign-in field to username would leave the existing required registration email and these criteria untouched. Native Apple support can start with the capability on a new primary App ID ahead of the first App Store release. [Apple capability setup](https://developer.apple.com/help/account/capabilities/about-sign-in-with-apple)

## What the current code changes about the plan

- The [member login page](../web/src/app/auth/login/page.tsx) uses hosted Keycloak sign-in when configured. The fallback password form and password registration still use the existing Java API. [KeycloakAuthService](../api-java/src/main/java/com/illamhelp/api/auth/KeycloakAuthService.java)
- The [registration controller](../api-java/src/main/java/com/illamhelp/api/auth/AuthController.java) validates legal acceptance, creates the profile and records policy versions. A first broker login bypasses that endpoint. Reuse its acceptance and profile services in an idempotent onboarding step.
- The web session provider uses an opaque session cookie for hosted login. The Next.js handler forwards authenticated REST and gRPC-Web requests using server-side tokens. Web registration still starts an existing Java API session during rollout. [Web session provider](../web/src/components/session/SessionProvider.tsx)
- The [local bootstrap](../scripts/keycloak-dev-bootstrap.sh) configures the application client and roles. [Compose](../infra/docker-compose.yml) and [Helm](../charts/illamhelp-local-infra/values.yaml) pin Keycloak 26.8.2. Use the existing provisioning and deployment process to reproduce social configuration.

## Delivery order

1. **Build the shared web flow.** Provision a dedicated confidential member-web client with authorization code and S256 PKCE. Register exact HTTPS callbacks separately for staging and production. Each provider redirects to the broker endpoint shown by Keycloak. Keycloak then redirects to the IllamHelp callback. Use a same-origin web session handler to start the flow, allowlist providers and local return paths, and bind expiring state, nonce and the PKCE verifier to the browser. Exchange the code server-side once and validate issuer, audience, nonce and signature. Keep refresh tokens server-side behind a Secure, HttpOnly session cookie with CSRF protection. Adapt SessionProvider to read session status and the member profile through that handler, including after reload. The server attaches the access token when forwarding requests to the API. Refresh and terminate the session with the issuing client. Verify API audience and role mapping with a real staging token.
2. **Create one profile per member from day one.** Use the realm subject as the internal user ID and let Keycloak bind each external provider identity. For an existing email match, require proof of the existing account before linking. Support linking from an authenticated member session after reauthentication. For a new member collect missing required fields, confirm a public username, and explicitly record current Terms and Privacy versions. Enforce incomplete onboarding on the API before member actions. Keep contact details private under existing rules. Provider sign-in grants neither a verification badge nor a staff role. Test staff account collisions and enforce the admin authentication policy even if a browser already has a member realm session.
3. **Pilot Google.** Register a web OAuth client and the broker callback. Configure audience, branding and consent for public use. Request only openid, email and profile. Add “Sign in with Google” on member sign-in and registration behind a flag. Test a new account, a returning account, an existing password member, a cancelled login and sign-out on a shared device. [Google OIDC guide](https://developers.google.com/identity/openid-connect/openid-connect) · [Google branding and artwork](https://developers.google.com/identity/branding-guidelines)
4. **Add Facebook.** Configure the built-in connector, a Meta app, strict redirect URI, privacy URL and data-deletion instructions or callback. Limit permissions to basic profile and email. If email is absent, collect and verify it before completing onboarding. Verify current access requirements in the app dashboard and complete a public-mode sign-in using an account outside the app’s tester roles before enabling the button. [Meta permissions walkthrough](https://developers.facebook.com/docs/graph-api/get-started/) · [Facebook Login changelog](https://developers.facebook.com/docs/facebook-login/changelog/)
5. **Qualify the native store builds.** Use platform-specific Keycloak clients and system authentication sessions with PKCE for Google and Facebook. For iPhone enable the Sign in with Apple capability for the bundle ID, present the native Apple option with equivalent prominence and test both Share My Email and Hide My Email. Accept the relay address throughout onboarding and recovery. Support returning users when Apple omits the initial name. Prove the server validates Apple’s response (signature, issuer, bundle audience, expiry and transaction-bound nonce), maps the stable Apple subject to the same member identity system, and establishes an IllamHelp session through a supported Keycloak integration. Gate iOS social login on this end-to-end test. Verify sign-in, linking, cancellation, return to the app and logout on both store release builds. [Apple capability setup](https://developer.apple.com/help/account/capabilities/about-sign-in-with-apple)

6. **Retire obsolete API handlers after password sign-in passes on every client.** Move the native member clients to system-browser authorization and the admin web client to its staff-only browser flow. Update the Bruno login helper, Playwright sign-in assertions, local fixtures and CI setup that call the old endpoints. Exercise clean registration and seed test users on a disposable realm. Once all callers use the new flow, remove the application password grant and obsolete API login, registration, refresh and logout handlers. Retain the onboarding and legal acceptance services. Check bootstrap and service credentials separately before disabling any realm-wide grant.

## Configure member web on staging

1. Create confidential client `illamhelp-member-web` in the existing realm. Enable Standard flow, require S256 PKCE, and use the exact redirect URI `<web-origin>/auth/oidc/callback`. Disable direct grants for this client. Use the realm signing algorithm RS256 for ID tokens. Add an Audience mapper that includes the existing application API client ID in **access tokens**.
2. For Google, configure the built-in provider with alias `google` and its Keycloak broker callback in Google Cloud. Keep the first-broker flow set to require proof of control of the existing IllamHelp account before linking. Validate Google’s verified-email behavior, and prevent any provider-supplied role mapping. For recovery, enable Forgot password in Keycloak and configure SMTP. [Keycloak administration guide](https://www.keycloak.org/docs/latest/server_admin/)
3. Supply the web app with `WEB_AUTH_ORIGIN`, `WEB_AUTH_ISSUER`, `WEB_AUTH_CLIENT_SECRET` and `WEB_AUTH_REDIS_URL`. Use HTTPS public origins outside localhost. Set `WEB_AUTH_INTERNAL_ISSUER` only if the web server reaches the same realm through an internal address. Set `WEB_AUTH_API_URL` (include the API prefix) and `WEB_AUTH_MEDIA_URL` to the REST and gRPC-Web upstreams reachable by the web deployment. In Helm set `web.memberAuthSecretName` to an existing Secret containing these variables. Use the deployment's existing secret provisioning. Omit query strings for the OAuth callback in ingress access logs.
4. Set `WEB_AUTH_GOOGLE=true` when the broker is configured and `WEB_AUTH_PASSWORD_RESET=true` when the realm reset and SMTP are ready. The application’s existing password form is used when the dedicated web client configuration is absent. Password account creation continues through the existing registration form during this rollout.

### Reproduce the staging infrastructure

- In the infrastructure chart, set `keycloak.publicUrl`, `keycloak.persistence.enabled=true` for the local Keycloak database, and `keycloak.memberWebSecretName` to the bootstrap Secret. The hook reads `WEB_AUTH_ORIGIN`, `WEB_AUTH_CLIENT_SECRET`, and optional `KEYCLOAK_SMTP_CONFIG` (Keycloak SMTP JSON). Point hosted Keycloak at a managed database and relay. For the isolated local stage set `mailpit.enabled=true` and use the Mailpit Service on port 1025. Keep its HTTP inbox accessible over a loopback port-forward only.
- When adding local persistence to an existing nonpersistent Keycloak Deployment, switch its strategy to Recreate and clear the stored rolling update settings before the Helm upgrade. Use the same values and Secrets on later upgrades. Keep the HTTPS TLS Secret separate from the auth and SMTP configuration.
- In the app chart, set `config.keycloakIssuerUri` to the public realm URI, `config.keycloakJwkSetUri` to the internal signing keys endpoint, and `web.memberAuthSecretName` to the web auth Secret. For public HTTPS use the configured ingress controller, `ingress.tls` and `ingress.keycloakHost`. For this controller-free kind cluster use `envoy.memberHttps.tlsSecretName` and forward local port 3443 to service `illamhelp-app-envoy` port 9443.
- The exact provider broker paths are `/realms/illamhelp/broker/google/endpoint` and `/realms/illamhelp/broker/facebook/endpoint` on the registered public Keycloak origin. The member web client redirect remains `/auth/oidc/callback` on the member web origin. Store provider credentials in managed secrets and use dedicated tester accounts. [Google OAuth client setup](https://support.google.com/cloud/answer/15549257) · [Keycloak server administration](https://www.keycloak.org/docs/latest/server_admin/)

### Enable Facebook after the staging sign-in checks

1. Configure the built-in Keycloak Facebook broker with alias `facebook`. Use the broker’s exact HTTPS callback in the Meta app and store the app credentials in the realm's existing secret-management process. Request only basic profile and email. Keep **Trust Email** off for Facebook and require the first-broker flow to collect a missing email and verify it before handing off to IllamHelp. Existing-account matches require proof of account control before linking. Keep the provider hidden on the generic Keycloak sign-in screen so IllamHelp can control where the Facebook option is offered. [Keycloak Facebook configuration](https://www.keycloak.org/docs/latest/server_admin/#_facebook)
2. Set `WEB_AUTH_FACEBOOK=true` on the staging web workload after the broker is ready. Verify cancellation, new and returning members, an existing password account, and a Facebook account that withholds email. Confirm a new member stays in onboarding until completing profile and policy acceptance. [Meta Facebook Login](https://developers.facebook.com/documentation/facebook-login/userexperience)
3. Supply the Meta app's privacy and data-deletion details. Verify the public app with an account outside the Meta tester roles before enabling the flag for members. [Meta platform policies](https://developers.facebook.com/devpolicy/)

## Release gates and recovery

| Gate | Evidence required |
| --- | --- |
| Email and password | With every social provider disabled, register a password-only member on staging, sign out, sign in by email, reset the password via email, and sign in again. Cover desktop and mobile web, Android and iPhone. Also verify username sign-in and password sign-in after optional provider linking. |
| Account linking | A newly created test member who adds a second sign-in method retains the same user ID, jobs, applications and sharing preferences. Duplicate callbacks produce one profile and one acceptance per policy version. Unproven email collisions cannot open an existing account. |
| Session and isolation | Test reload, expiry, refresh, logout, denied consent, invalid state, repeated callback and provider outage. Direct provider tokens cannot call member APIs. Incomplete members cannot bypass onboarding. Staff access still requires the existing staff controls. |
| Member experience | Run Playwright with a controlled test identity provider on desktop and mobile viewports in both themes. Separately exercise each real provider on staging HTTPS, including iPhone Safari and Android Chrome, missing email, back navigation, and recovery through another sign-in method. |
| Operations | Deploy via existing Helm/Compose configuration with secrets injected per environment. Collect aggregate outcomes by provider and failure stage. Exclude tokens, authorization codes and personal details from logs and analytics. Test key rotation and alert on elevated callback or refresh failures. |
| Rollback and recovery | Disable new logins per provider while preserving identity links. Verify how existing sessions expire. Before broad rollout, give social-only members a verified recovery or second sign-in method and test it during a provider outage. |
